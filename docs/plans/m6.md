# M6 execution plan: multi-agent team, MCP server and channels

**Brief:** *Multi-agent team (Triage, Policy RAG, Order-Actions, Escalation Reviewer) with an MCP server exposing order/refund/shipping mock APIs so the same tools work across chat and email channels.*

**Status:** Done (2026-10-11), Azure items deferred. The owner asked for M1–M8 to be completed without interruption, so this plan is recorded and built straight away. Items that need a person or Azure consent are listed under Deferred.

## Decisions
| # | Decision | Why |
|---|---|---|
| M6-1 | **MCP server** is a workspace member `services/mcp_server` (package `mcp_server`), built on the official `mcp` SDK v1 (`FastMCP`), streamable HTTP, stateless | LLD-2 service layout; LLD-4 L4e |
| M6-2 | **Two endpoints**: `/mcp/read` (read tools; agents) and `/mcp/system` (write tools; code only), enforced by scope in the caller context | LLD-4 L4a. An agent cannot reach a system tool, and this is tested |
| M6-3 | **Caller context** is an HMAC-SHA256 token in `X-Caller-Context` (customer, scope, 5-minute expiry), signed with a shared key in `libs/contracts`; tools take no customer ID | LLD-4 L4b; prompt injection cannot choose a customer |
| M6-4 | **Four agents as graph nodes**: Triage (LLM), Policy RAG (rules engine + cited answer), Order-Actions (LLM, read-only tools), Escalation Reviewer (LLM, no tools, writes a brief for the human reviewer) | Brief |
| M6-5 | **Refunds are still executed by code** after the risk gate; the Order-Actions agent proposes nothing that is written | D10 |
| M6-6 | **Two channels**: chat (`POST /v1/chat/tickets`) and email (`POST /v1/channels/email/inbound`, the payload a Logic App would send). Both call the same graph | Brief; LLD-7 |
| M6-7 | **Email rule**: a refund from email always goes to approval; the sender must be a registered customer (D8d) | Design D8d |
| M6-8 | **Parity suite**: the same ticket via chat and via email reaches the same eligibility and decision, except the email refund route, which is always approval | Acceptance |

## Components
| Component | Location |
|---|---|
| Caller context (sign and verify) | `libs/contracts/src/shopsense_contracts/caller_context.py` |
| MCP server (read and system servers, auth middleware, tools) | `services/mcp_server/src/mcp_server/` |
| MCP client adapter implementing `OrderTools` | `services/shopsense_api/src/shopsense_api/adapters/orders/mcp_order_tools.py` |
| Read-only Order-Actions agent (no write tools offered) | `application/agents/order_actions.py` (`read_only`) |
| Escalation Reviewer agent (no tools) | `application/agents/escalation_reviewer.py`, prompt `reviewer/v1.md` |
| Policy node (rules engine, cited answer for policy questions) | `application/use_cases/decide_return.py`, `answer_policy.py` |
| Channels: chat and email HTTP API | `services/shopsense_api/src/shopsense_api/adapters/http/app.py` |
| Registered senders (email → customer) | `data/registered_senders.json` |

## Deferred (needs the owner or Azure consent)
- Azure Container App for the MCP server, Logic App on a real support mailbox (OAuth consent), and the Storage queue for replies. Local equivalents are used for the evidence: the MCP server runs locally, and the email channel is exercised by posting the Logic App payload.

## Acceptance
- Read tools reachable by agents; system tools refused on the read endpoint (tested).
- A forged or expired caller context is refused (tested).
- Parity suite: chat and email agree; email refunds always route to approval.
- Agents expose no write tool to the model.
- ruff, mypy strict, pytest pass.

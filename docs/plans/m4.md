## Decisions
| # | Decision | Why |
|---|---|---|
| R4-1 | **Rules engine decides eligibility in code** (LLD-6 L6c, L6d); RAG only explains and cites | An LLM must never decide a window or amount |
| R4-2 | **Hybrid retrieval**: dense (`text-embedding-3-small`) + sparse keyword vectors computed locally, fused with **reciprocal rank fusion (k = 60)** in code over two Qdrant queries | Qdrant local mode does not run server-side prefetch fusion; the two-query form is equivalent and testable |
| R4-3 | **Reranker behind a `Reranker` port**: local ONNX cross-encoder (fastembed, `Xenova/ms-marco-MiniLM-L-6-v2`); Cohere via Foundry not deployed on the trial | L6f fallback is the implemented path; the Foundry Cohere deployment is deferred |
| R4-4 | **Collection `policy_chunks_v2`** with named dense and sparse vectors; M3's collection stays untouched | Changing vector layout in place is unsafe; ingestion takes `--rebuild` to ignore stored hashes |
| R4-5 | **Citation-time consistency**: the chunk hash in the index must equal the hash of the section in the corpus files; mismatch → escalate | LLD-6 L6g |
| R4-6 | **Numeric fabrication check**: every number in an open-question answer must occur in the cited sections, else the answer falls back to a hand-off | Brief: never invent a window or amount |
| R4-7 | **Groundedness** scored by an LLM judge (gpt-4.1-mini, prompt `judge/v1`) over answered questions, 1–5 | Azure AI evaluation SDK needs a Foundry project and key-based auth; the judge is reproducible with the existing gateway. Documented as a deviation |

## Rules engine
Inputs are system facts only: category, is_accessory, item condition, payment method, delivery date, report time, today (IST).

1. Candidates: rules of kinds `return_window`, `not_returnable`, `exception` whose conditions all match the case. Conditions: `category`, `is_accessory`, `item_condition`, `payment_method`, `reported_within_hours` (case reported within N hours), `price_below_paise`.
2. Overrides: a candidate named in another candidate's `overrides` is removed.
3. Specificity: the candidate with the most conditions wins.
4. Tie: two remaining candidates with equal specificity and different outcomes raise `PolicyTie` (fail closed; the tie is reported with both rule IDs).
5. Window: days = calendar days in IST between delivery and today; eligible when days ≤ window_days (day 15 is the last day for a 15-day window).
6. Evidence: a rule with `requires_evidence: photo` returns `needs_evidence` until a photo is verified.

Corpus changes needed for these semantics (made in M4, documented in each document):
- `GW-500` kind becomes `goodwill` and `CAN-PRE-DISPATCH` becomes `cancellation`, so neither competes with return windows.
- `DMG-48H` and `WRG-MIS-48H` override the category windows they replace; `GRO-DMG-48H` overrides `DMG-48H` for groceries (replacement only).

## Retrieval
| Stage | Method |
|---|---|
| Dense | Qdrant query over `dense` (top 20) |
| Sparse | Qdrant query over `sparse` keyword vector, hashed terms with log-scaled frequency (top 20) |
| Fusion | Reciprocal rank fusion, k = 60, then category filter already applied in both queries |
| Rerank | Cross-encoder over the fused top 20, keep top 4 |

Comparison reported on the same 31 questions: dense, hybrid, hybrid + rerank. Conflict traps (questions with a category) report precision@1 for the category-specific section.

## Safety checks on answers
- Citation check (M3): every citation was retrieved.
- Consistency check (R4-5): cited chunk hash equals the corpus hash.
- Numeric fabrication check (R4-6): numbers in the reply occur in the cited text.

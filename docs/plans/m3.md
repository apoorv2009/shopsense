# M3 execution plan: memory and policy index

**Brief:** *Persistent per-customer memory (past tickets, preferences) + a Qdrant index over returns/shipping/warranty policy documents.*

**Status:** Done 2026-10-11 (Q1–Q4 as recommended). Results: [milestones/m3](../../milestones/m3/README.md). Deviation: the Qdrant Container App is deferred to M8 packaging; embedded Qdrant is used until then.

## Decisions
| # | Question | Decision | Why |
|---|---|---|---|
| Q1 | Where does Qdrant run? | **Container App with ephemeral storage, external ingress + API key, scale 0–1; index rebuilt by an idempotent ingestion step** (demo and eval scripts ingest first). Tests and CI use the Qdrant client's in-process local mode. Amends [D6](../adr/006-data-stores.md) (Azure Files dropped) | Qdrant does not support network file systems (Azure Files = SMB); the index is derived data (source of truth: policy files in git + rules table in PostgreSQL), so rebuilding is cheap and safe; scale-to-zero keeps trial cost near zero |
| Q2 | Who writes the one-line ticket summary? | **Code, from a template over system facts** (issue type, order, outcome, amount) | Customer text never reaches memory ([D9](../adr/009-conversation-and-memory.md) anti-poisoning rule) |
| Q3 | Where is memory used at M3? | **Order-Actions agent receives a trusted "customer context" block** (recent tickets, preferences) built by code; after each run the outcome is written back | Shows recall end to end before the LangGraph workflow (M5) takes over loading and writing |
| Q4 | How is retrieval measured? | **~30 labelled policy questions** → expected `doc_id#section`; report hit@4 and MRR@10 (dense baseline) | Baseline M4's hybrid + rerank must beat |
| Q5 | Where does ShopSense data live? | Second database `shopsense` on the existing PostgreSQL server; own Alembic migrations (same pattern as the Order Platform) | [D6](../adr/006-data-stores.md), [LLD-3](../lld/03-data-models.md) |
| Q6 | Embeddings | `text-embedding-3-small` (1536 dims) deployed on the existing Foundry resource, behind an `Embedder` port; deterministic fake embedder in tests | [L3g](../lld/03-data-models.md) |
| Q7 | Rules at M3 | Rules blocks parsed, schema-validated and checked against their section text at load, then stored versioned in `policy_rules`. The deciding rules engine is M4 | [Milestone plan](../02-milestone-plan.md) |

## Policy corpus
14 synthetic but realistic Indian e-commerce policy documents in `data/policies/`, each section followed by a fenced `rules` block ([LLD-6](../lld/06-rules-engine-and-retrieval.md)). The corpus deliberately contains conflicting category windows (general 30, electronics 15, accessories 7, apparel 45, groceries non-returnable).

| # | doc_id | Topic |
|---|---|---|
| 1 | `returns-general` | General return policy (30 days) |
| 2 | `returns-electronics` | Electronics addendum (15 days) |
| 3 | `returns-electronics-accessories` | Accessories (7 days) |
| 4 | `returns-apparel` | Apparel and footwear (45 days, tags on) |
| 5 | `returns-groceries` | Groceries (non-returnable; damaged/expired exception) |
| 6 | `returns-home-kitchen` | Home and kitchen |
| 7 | `returns-beauty` | Beauty and personal care (hygiene: unopened only) |
| 8 | `damaged-wrong-missing` | Damaged, wrong or missing items (48 h, photo evidence) |
| 9 | `refund-methods` | Refund methods and timelines by payment method |
| 10 | `shipping-delivery` | Shipping charges, delivery timelines, delays |
| 11 | `order-cancellation` | Cancellation before and after dispatch |
| 12 | `warranty` | Manufacturer and seller warranty, repair or replace |
| 13 | `cash-on-delivery` | COD refunds (bank transfer / store credit) |
| 14 | `goodwill-compensation` | Goodwill credits (max ₹500), escalation |

## Components
| Layer | Component |
|---|---|
| Domain | `CustomerMemory`, `TicketRecord`, `CustomerPreferences` (allowed values only), `summarize_ticket()` template; `PolicyDocument`, `PolicySection`, `PolicyRule`; rules-block parser and load-time validation |
| Application | Ports `MemoryStore`, `Embedder`, `PolicyIndex`, `PolicyRepository`; use cases `RecallCustomer`, `RememberTicket`, `IngestPolicies` (skips unchanged content hashes), `SearchPolicy`, `AnswerPolicyQuestion` (answers only from retrieved sections; citations must be a subset of retrieved IDs, else fail closed); Order-Actions agent accepts an optional customer context |
| Adapters | `adapters/db/` (tables `tickets`, `ticket_history`, `customer_profiles`, `policy_documents`, `policy_rules`; Alembic baseline; SQL stores), `adapters/vector/qdrant_index.py`, `adapters/llm/foundry_embedder.py` |
| Entrypoints | Settings (`SHOPSENSE_DATABASE_URL`, `SHOPSENSE_QDRANT_URL`, `SHOPSENSE_QDRANT_API_KEY`, embedding deployment), composition, `shopsense-ingest` CLI |
| Evals | `evals/data/retrieval.jsonl` (~30), `shopsense-eval retrieval` |
| Infrastructure | `infra/m3/`: embedding deployment, `shopsense` database, Container Apps environment + `qdrant` app |

## Tests
| Level | Coverage |
|---|---|
| Unit | Parser (valid, missing fields, window not in text), summary template, recall/remember with in-memory stores, ingestion skip-unchanged, citation subset check, agent context injection |
| Integration | SQL stores + migrations drift test against PostgreSQL (CI service container); Qdrant adapter in local mode |
| Eval | Retrieval suite against the live index (one smoke run, per the evaluation cadence agreed for M3–M7; full ×3 runs after M8) |

## Acceptance
- ruff, mypy `--strict`, pytest pass.
- Memory: a returning customer's past tickets and preferences are recalled; memory contains no customer free text.
- Ingestion is idempotent (second run indexes 0 changed sections).
- Retrieval baseline reported (hit@4, MRR@10).
- Demo: returning customer recognised; policy question answered from retrieved sections with citations.

## Deferred to M4
Sparse vectors and RRF fusion, reranker, rules engine decisions, precedence tie detection, citation-time hash check, groundedness evaluation.
